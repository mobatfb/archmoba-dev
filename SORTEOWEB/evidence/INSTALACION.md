# SORTEOWEB 1.2.0 — reglas, cierre y evidencia

## Instalar
1. Respalda la base de datos y los archivos de la instalación 1.1.10. Importa `database/migrations/1.2.0.sql` en la base existente (requiere migraciones previas hasta 1.1.6). Extrae el parche sobre el sitio incluyendo los `.htaccess`. No reemplaza credenciales ni datos de conexión. Comprueba que los archivos internos no sean descargables por HTTP.
2. Habilita PHP 8.1+ con PDO MySQL, Sodium y ZIP/libzip con cifrado AES-256. Desde la versión 1.2.8, la primera activación de un sorteo crea automáticamente `evidence/config.local.php` con una clave aleatoria de 32 bytes y permisos 0600, siempre que PHP pueda escribir en esa carpeta y todavía no existan evidencias cifradas. Si ya existe una clave (o `SW_EVIDENCE_KEY`), se conserva. Si faltara después de crear evidencias, restaura la original; no generes otra. Respalda el archivo en un lugar seguro, no lo publiques ni lo reemplaces. Como alternativa inicial, antes de crear evidencias, puedes usar `php evidence/init-key.php` desde Terminal.
3. En cPanel → Trabajos de cron, crea una tarea cada minuto que ejecute `php /RUTA/ABSOLUTA/sorteos/evidence/cron.php` usando la versión PHP que tiene las extensiones indicadas. El cierre por capacidad también se comprueba en el registro de pagos y al cargar vistas; el cron es necesario para cerrar por fecha incluso sin visitas. Comprueba el log de ejecución.
4. Crea un borrador con el tipo de premio, modalidad, valor y condición de cierre. Si es producto, ordena fotos con flechas o arrastrando. Si es dinero, la imagen fija y descripción se asignan automáticamente. La fecha es hora de Ecuador; en capacidad exclusiva se venden todos los números; en capacidad compartida se establece un máximo de participaciones (pagadas para el cierre, pendientes reservan cupo).
5. Al activar, se selecciona un número aleatorio con `random_int`, se crea una imagen SVG del boleto y un manifiesto JSON dentro de un ZIP AES-256. El ZIP y SHA-256 se publican antes de vender; el número y la contraseña se guardan con Sodium secretbox. El administrador no puede editar ni reactivar sorteos nuevos publicados. El control del servidor podría revelar anticipadamente el resultado; el hash verifica integridad, no imparcialidad. Mantén una copia del hash publicado fuera del sitio.
6. El cierre selecciona titulares pagados del número preseleccionado, reparte el premio con redondeo a centavos en orden estable de ID, y revela el ZIP. Si es producto compartido: un titular recibe el producto; varios reciben el equivalente económico previamente indicado. Si no hay titular pagado o el sorteo exclusivo termina por fecha sin venta completa, se registra devolución pendiente de revisión, no se elige otro ganador. No se transfiere dinero automáticamente. La modalidad compartida limita una participación por cuenta y número; verificar la identidad real requiere un proceso adicional. Los sorteos legacy activos y finalizados mantienen su configuración y no reciben evidencia retroactiva. Revisa/guarda los borradores antiguos para asignar reglas nuevas.
7. PayPhone, compra de boletos por saldo y pagos reales continúan deshabilitados; la versión permite registros manuales autorizados y consulta de disponibilidad. No hay autorización financiera implícita. Prueba con datos de ensayo, no con dinero real. La ejecución de la migración y la generación del ZIP AES-256 deben validarse en el hosting antes de abrir al público.
